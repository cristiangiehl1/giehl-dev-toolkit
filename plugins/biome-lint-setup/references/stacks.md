## Next.js full-stack

Applied automatically by the script when `next` is present in the dependencies.

```jsonc
{
  "linter": {
    "domains": { "next": "recommended", "react": "recommended", "tailwind": "recommended" }
  },
  "files": {
    "includes": ["**", "!**/.next/**", "!**/out/**", "!**/next-env.d.ts"]
  }
}
```

The `next` domain replaces `eslint-config-next` (core-web-vitals + typescript): it turns on `useExhaustiveDependencies`, the `next/image`/`next/head` rules, and the React hooks set. There is no need to list rules one by one.

**Ignoring `next-env.d.ts` is not optional** — the file is regenerated by Next on every build, and formatting it creates a dirty diff on every commit.

**Server Actions and `'use server'`/`'use client'`:** Biome preserves the directives normally; there is no special configuration. If `organizeImports` moves something above the directive, that is a bug — report it, but in practice it respects the position.

## Next.js + separate Node API (monorepo)

Two packages with partially different styles. The structure that works:

```
repo/
├── biome.json           # root: shared formatting, "root": true (default)
├── .editorconfig        # here only
├── .nvmrc               # here only
├── apps/web/biome.json  # "root": false + next/react/tailwind domains
└── apps/api/biome.json  # "root": false + framework delta
```

Run the script once per package:

```bash
node scripts/setup-biome.mjs --dir apps/web
node scripts/setup-biome.mjs --dir apps/api --nested --framework hono
```

Note that `apps/web` runs **without** `--nested` only if it is the effective root of the repo. In a real monorepo structure, both take `--nested` and the root gets a `biome.json` with whatever is shared.

Points that usually bite:

- **`"root": false` is mandatory** in the packages. Without it: `Found a nested root configuration, but there's already a root configuration` and nothing runs.
- **Inheritance is not automatic.** A nested `biome.json` *replaces* the sections it declares; to genuinely inherit, use `"extends": ["../../biome.json"]` and declare only the delta.
- **`.editorconfig` with `root = true` only at the root.** A nested `root = true` cuts off inheritance from the one above — that is why the script skips these files under `--nested`.
- **`vcs.useIgnoreFile`** reads the `.gitignore` of the config's directory. In a package with no `.gitignore` of its own, keep the `vcs` block at the root only.

## Vite / SPA frontend-only

```jsonc
{
  "linter": {
    "domains": { "react": "recommended", "tailwind": "recommended", "test": "recommended" }
  },
  "files": { "includes": ["**", "!**/dist/**"] }
}
```

No `next` domain (there is no Next). The `test` domain comes in when there is `vitest`/`jest` — it relaxes rules that only make sense in production code and turns on the test-specific ones.

Since there is no server layer, the `recommended` preset already covers things well. The practical difference compared to Next is that a11y rules show up more strongly in an SPA — `useButtonType`, `useKeyWithClickEvents`, `useAltText`. They are worth fixing rather than disabling: they are real accessibility bugs that `eslint-config-next` let through.

## Node backend

Base shared by all frameworks — no React, no Tailwind, no CSS:

```jsonc
{
  "linter": { "rules": { "preset": "recommended" } },
  "files": { "includes": ["**", "!**/dist/**"] }
}
```

One adjustment that applies to any backend: if the project uses `process.env` all over the place, `noProcessEnv` (when enabled) will complain. It is not part of the recommended preset, so it stays quiet by default — only turn it on if the project has a central env module (e.g. Zod validation), otherwise it is just noise.

### Hono

**Nothing to adjust.** Tested with middlewares, typed context (`Hono<Env>`), `onError`, and async handlers: it passes clean on the `recommended` preset.

If you use `hono/jsx` instead of React, configure the runtime in `tsconfig.json` (`jsxImportSource: "hono/jsx"`) — Biome follows the tsconfig and needs no config of its own. Do not turn on the `react` domain in a Hono JSX project: the hooks rules do not apply and produce false positives.

### Fastify

No config adjustment. The only friction is the plugin `opts` you do not use:

```ts
// triggers noUnusedFunctionParameters
async function dbPlugin(fastify: FastifyInstance, opts: FastifyPluginOptions) {}

// clean — the signature still has arity 2
async function dbPlugin(fastify: FastifyInstance, _opts: FastifyPluginOptions) {}
```

Prefixing with `_` is preferable to disabling the rule: the signature Fastify expects is preserved and you keep the check on the rest of the code.

Declaration merging (`declare module 'fastify' { interface FastifyInstance { ... } }`) works with no configuration.

### Express

No config adjustment. The classic friction is the error middleware, which Express **only recognizes with arity 4** — even when `next` is unused:

```ts
// triggers noUnusedFunctionParameters on _req and next
export function errorHandler(err: Error, req: Request, res: Response, next: NextFunction) {
  res.status(500).json({ message: err.message })
}

// clean, and Express still recognizes it as an error handler
export function errorHandler(err: Error, _req: Request, res: Response, _next: NextFunction) {
  res.status(500).json({ message: err.message })
}
```

Resist the temptation to disable `noUnusedFunctionParameters` globally because of a handful of handlers — the rule catches real bugs in controllers.

### NestJS

The only framework that needs real configuration. The script applies:

```jsonc
{
  "javascript": {
    "parser": { "unsafeParameterDecoratorsEnabled": true }
  },
  "linter": {
    "rules": {
      "style": { "useImportType": "off" },
      "correctness": { "noUnusedFunctionParameters": "off" }
    }
  }
}
```

Why each one:

1. **`unsafeParameterDecoratorsEnabled`** — without it Biome **fails at the parser**, not at the linter: `Decorators are not valid here` on every constructor `@Inject()`/`@InjectRepository()`. The whole file is discarded. If a Nest project looks like it "isn't being linted", this is why.

2. **`useImportType: "off"`** — the rule would convert `import { Repository } from 'typeorm'` into `import type { ... }`. With `emitDecoratorMetadata`, TypeScript uses those imports at runtime to build `design:paramtypes`; turned into a type-only import, the metadata disappears and **dependency injection breaks at runtime**, with no compile error. It is the kind of breakage that only shows up in production.

3. **`noUnusedFunctionParameters: "off"`** — parameter properties (`constructor(private readonly repo: Repository<User>)`) are read as unused parameters. Here the `_` convention does not help, because the parameter name *is* the property name (`this.repo`). Disabling is the correct way out.

Nest's `tsconfig.json` must keep `experimentalDecorators` and `emitDecoratorMetadata` — Biome does not change that, but confirm they are still on after the migration.
